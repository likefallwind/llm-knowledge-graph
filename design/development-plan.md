# AI 全领域知识图谱：下一阶段开发计划

## 1. 目标

本项目的目标不变：让 LLM 持续阅读高质量 AI 语料，从中抽取、判断、对齐并
逐步合并知识，形成覆盖人工智能主要知识体系、可以追溯到原文、可以用于知识
导航和个性化教学的知识图谱。

唯一主流程仍然是：

```text
Read → Extract → Resolve → Merge → Repeat
```

下一阶段不重新设计知识模型，重点是让已经实现的核心闭环在多来源语料上持续
工作，并根据真实运行中反复出现的问题做少量、可验证的改进。

## 2. 开发原则

### 2.1 LLM 驱动，语料提供知识

- LLM 负责阅读、抽取、类型判断、实体消歧、规范命名和关系证据裁判。
- 程序负责 Passage 定位、Evidence 保存、幂等、事务、自环和循环等硬约束。
- LLM 参数记忆不能成为 Entity 或 Claim 的来源。
- 每个进入正式图谱的 Entity 和 Claim 都必须能回到 Source 中的真实原文。

### 2.2 保持最小模型

继续只保留四类知识对象：

```text
Source / Entity / Claim / Evidence
```

Entity 类型继续使用：

```text
resource / criterion / data / task / solution / concept
```

Claim 关系继续使用：

```text
is_a / part_of / prerequisite_of
```

ClaimObservation、alias 和运行进度是实现核心闭环所需的记录，不扩展成新的知识
对象或复杂状态机。

### 2.3 人工只做偶尔观察

- 可视化的主要用途是让图谱结构、原文 Evidence 和模型判断保持透明。
- 人可以偶尔浏览并指出明显问题，但不逐条审核，也不承担发布门槛。
- 当前不开发标注系统、审核后台、任务分发或综合评分体系。
- 只有真实运行中反复出现、具有普遍意义的错误，才保留为少量回归样例。

### 2.4 根据真实问题迭代

每次算法或提示词修改必须对应一个已经观察到的问题。优先修改 ontology 定义、
提示词示例、模型可见上下文或简单的确定性约束，不因单条坏数据增加个案规则。

## 3. 当前起点

当前实现已经具备：

- Source 版本化、PDF/HTML/JSONL/文本读取和稳定 Passage；
- 带 Source Evidence 的 Entity 与 Claim 抽取；
- `same / new / uncertain` 实体身份判断；
- Claim 关系证据裁判和多 Evidence 累积；
- ClaimObservation 持久保存、待定端点重放和 Entity 晋升；
- Chunk 级事务、幂等和断点续跑；
- 图谱完整性检查、审计和可搜索的交互式可视化；
- MiniMax M3 严格 JSON 修复和至多一次相同请求重新生成。

当前正式数据库 `data/knowledge.db` 与历史复杂数据库 `data/kg.db` 必须继续分开。
下一阶段先在新的实验数据库中验证最新流程，验证完成前不覆盖正式库。

## 4. 里程碑一：验证最新 Observation 闭环

### 目标

证明 LLM 已经从 Source 中抽出的有效关系观察，不会因为端点暂时不存在、裁判
暂时失败或关系暂时无法落实而永久丢失。

### 工作

1. 使用最新代码创建一份全新的实验数据库。
2. 先对《神经网络与深度学习》运行一个有界批次。
3. 检查 Entity、Claim、Evidence、ClaimObservation 和裁判记录是否完整。
4. 对失败 Chunk 使用相同参数重跑，确认已完成 Chunk 不重复处理。
5. 执行 `replay-pending`，确认新增 Entity 或 alias 后可以使用已有裁判结果落实
   Claim，而不重新抽取 Source。
6. 执行 `kg check`、SQLite integrity check，并生成审计页面。
7. 有界批次稳定后，再完成该 Source 的剩余 Chunk。

### 完成条件

- 每个处理过的 Chunk 都有明确的 `done` 或可重试 `failed` 结果。
- 有效 Observation 在端点待定和 API 失败后仍可检查、可重放。
- 已落实 Entity 和 Claim 都有可定位 Evidence。
- 数据库完整性检查通过。
- 可视化可以查看正式图谱、待定 Observation、原文和裁判理由。

本里程碑只在真实运行暴露缺陷时修改代码，不为了运行本身增加调度框架或恢复
状态机。

## 5. 里程碑二：验证多来源持续合并

### 目标

让核心闭环从“读完一本书”进入“持续读不同来源并逐渐形成同一张图”。

### 语料顺序

优先选择内容有明显重叠的基础教材：

1. 《神经网络与深度学习》；
2. Stanford CS229 Machine Learning Notes；
3. Understanding Deep Learning；
4. PRML 或 Probabilistic Machine Learning。

重叠来源优先于互不相干的新领域，因为它们能直接暴露跨语言名称、别名、实体
重复和 Claim Evidence 累积问题。

### 每个 Source 的处理流程

```text
run Source
→ replay-pending
→ 有界 reconcile
→ kg check
→ audit / viz
→ 继续下一个 Source
```

### 重点观察

- 中英文名称能否通过 Evidence 判断为同一 Entity；
- 相似但不同的算法、模型和任务是否被保守地区分；
- 同一 Claim 是否自然累积来自不同 Source 的 Evidence；
- 不同教材的定义差异是否被分别保留；
- 新 Source 是否能解决旧的待定端点或孤立实体；
- `uncertain` 是否能随着新 Evidence 增加被重新判断。

字符串相似度只负责召回候选，不能自动合并。LLM 返回 `same` 时仍必须依据双方
定义和 Source Evidence；证据不足时保留 `uncertain`。

### 完成条件

- 至少出现一批可以直接检查的跨来源同一 Entity；
- 至少出现一批相同 Claim 的多来源 Evidence 累积；
- 待定 Observation 能因后续来源而自动落实；
- 没有为了提高连通性而放宽 Evidence 或自动合并边界。

这里以真实例子证明闭环是否成立，不把开发目标变成节点数、边数或综合统计量。

## 6. 里程碑三：基于真实失败改进 LLM 判断

### 目标

让 LLM 在持续阅读中逐步减少反复出现的语义错误，同时保持代码和规则简单。

### 处理顺序

发现明显问题后，依次判断它属于：

1. Source 或 Passage 读取问题；
2. 抽取提示词问题；
3. Entity 身份判断问题；
4. Claim 关系定义或证据裁判问题；
5. Observation 解析和物化问题。

一次只处理一类问题。修改后优先使用已经保存的 Observation 重新解析或重新裁判；
只有抽取本身发生变化时才重新读取和抽取 Source。

### 优先关注的已知边界

- `prerequisite_of` 必须表示原文明示的实质性学习前提，章节顺序、“奠定基础”
  或一般帮助关系不能自动进入正式 Claim；
- `part_of` 需要区分组成、正文明确列出的阶段和明确领域归属，不能由共现或
  “用于、涉及、尤其”等弱表达建立；
- `is_a` 必须通过实例测试，不能把领域归属、构件关系或名称包含误当成类属；
- 章节标题、习题描述和泛化短语只有在满足 Entity 定义时才能成为 Entity；
- 中英文规范名和 alias 的合并必须保留双方原始 Evidence。

### 完成条件

- 修改能够解释并修复一组同类真实错误，而不是只修复单个样本；
- 相关确定性测试和少量回归样例通过；
- 修改没有放宽“语料是唯一知识来源”的边界；
- prompt 或 ontology 语义变化时正确更新版本，旧结果不会被错误跳过。

## 7. 里程碑四：逐步扩大 AI 领域覆盖

### 目标

在多来源合并稳定后，从基础机器学习逐步覆盖 AI 的主要知识体系。

### 建议扩展顺序

1. 数学、概率和优化基础；
2. 统计学习与深度学习；
3. 图机器学习；
4. 强化学习；
5. 自然语言处理、语音和多模态；
6. 大语言模型、对齐与 RLHF；
7. AI 评测、安全和典型应用。

选择下一份 Source 时只回答两个问题：

- 它能否为已有 Entity 或 Claim 提供独立 Evidence？
- 它能否补充一个当前明显缺失的重要领域？

主动搜索只在已有语料长期不能解决重要孤立实体、身份歧义、关系证据或领域缺口
时使用。找到新语料后仍必须进入相同的 Read–Extract–Resolve–Merge 流程。

### 运行方式

- 新 Source 先做少量 Chunk 冒烟，再扩大到完整 Source；
- 长批次使用持久后台会话和明确的日志、数据库及完成标记；
- 可有界并行不同 Chunk 的无状态 LLM 抽取，并按原顺序消费；也可并行同一
  Chunk 中彼此独立的 Claim 裁判；Entity 对齐和图谱写入始终保持串行；
- 每个 Source 完成后运行 `replay-pending`、有界 `reconcile`、`check` 和 `viz`；
- 不因图谱变大引入服务层、任务平台或生产级并发架构。

## 8. 里程碑五：形成可用的知识导航

### 目标

让图谱不仅可以审计，还能自然支持学习和知识探索。

现有可视化继续作为最小入口，逐步围绕真实使用补充：

- 按规范名和 alias 搜索 Entity；
- 查看局部关系和相邻概念；
- 查看不同 Source 对同一 Entity 的定义 Evidence；
- 查看 Claim 为什么成立以及由哪些 Source 支持；
- 查看仍待解析或证据不足的 Observation；
- 区分 Source 明示的 `prerequisite_of` 与未来可能产生的教学建议。

可视化用于解释和浏览，不承担逐条人工标注、审核发布或直接修改数据库的职责。
只有真实使用证明现有页面不足时，才增加新的交互。

### 完成条件

使用者能够从图谱直接回答：

- 一个概念是什么；
- 它有哪些别名和不同来源定义；
- 它与哪些概念存在有据关系；
- 一条关系为什么存在；
- 学习一个概念前有哪些被语料明确支持的前提。

## 9. 正式数据库的推进边界

实验数据库满足以下条件后，才决定如何形成下一份正式数据库：

- 最新 Observation 闭环经过真实 MiniMax 批次验证；
- 多个 Source 能在同一数据库中持续处理；
- 跨来源 Entity 对齐和 Claim Evidence 累积已有可检查实例；
- `kg check` 与 SQLite integrity check 通过；
- 典型错误没有要求引入复杂工程机制才能继续运行。

正式推进时必须保留旧数据库备份，不覆盖 `data/kg.db`，并明确区分实验结果、
迁移结果和正式数据库状态。

## 10. 当前明确不做

- 不建设金标数据集或统计评测平台；
- 不把人工标注作为核心闭环或发布门槛；
- 不增加 `proposed / published / shadow` 等状态机；
- 不让 LLM 根据参数记忆直接补充知识；
- 不为了连通性自动接受实体合并或弱关系；
- 不提前增加新的 Entity 类型或 Claim 关系；
- 不引入 Neo4j、服务层、工作流编排、审核后台或生产级并发；
- 不一次性运行全部语料后再判断问题；
- 不以节点和边数量代替知识质量和可追溯性。

## 11. 近期执行顺序

下一轮开发按以下顺序进行：

1. 创建新的实验数据库并完成最新 Observation 流程的有界 NNDL 运行；
2. 检查待定 Observation、裁判缓存、重放和物化是否符合设计；
3. 修复真实运行中发现的核心闭环缺陷；
4. 完成 NNDL，并生成新的审计与可视化结果；
5. 加入 CS229，验证中英文实体对齐和跨来源 Evidence；
6. 加入 Understanding Deep Learning，继续验证重复实体和 Claim 聚合；
7. 只针对反复出现的语义错误做小范围 LLM 提示词或 ontology 改进；
8. 闭环稳定后，按领域逐步加入其余高质量语料；
9. 随图谱增长，以真实知识导航需求推动可视化改进。

每一步完成后再进入下一步，不同时展开语料扩张、关系扩张、复杂评测和工程架构
升级。整个开发过程始终服务于同一件事：让 LLM 能够以语料为唯一知识来源，
持续、保守、可追溯地构建覆盖 AI 领域的知识图谱。

## 12. 2026-08-01 首轮执行记录

已在隔离数据库完成 NNDL 前五个 Chunk 的真实 MiniMax M3 运行，并生成可搜索
的审计页面。`kg check`、SQLite integrity check 和 `replay-pending` 均通过；
正式数据库未改动。当前没有待定端点达到三个独立 Passage，因此没有为了减少
待定项而创建缺少稳定定义的 Entity。

运行中发现并完成两类最小修复：

1. schema 5 会在每次重新连接时把当前 Claim Evidence 再导入为 legacy
   Observation。schema 6 改为一次性回填，并只清理已有完整原生 Observation
   对应的精确重复项。
2. `part_of` 和 `prerequisite_of` 在三类重复语义边界上过宽。修复只修改 LLM
   可见的 ontology 排除项、反例和相关 prompt 版本；三条真实 Evidence 的独立
   复判都由 MiniMax M3 返回 `insufficient`。

用于续跑验证的命令曾与后续批次短暂重叠，同一个目录 Chunk 因而被 LLM 读取
两次。两次结果都有 Source Evidence，幂等键和完整性约束也没有损坏，但该实验
不用于比较数量；后续长批次保持单写者。

下一次运行先用更新后的 prompt 在全新实验数据库做小批量 smoke，确认完整
Read–Extract–Resolve–Merge 流程后再继续 NNDL。当前不据此建设人工标注、金标
或统计评测流程。
